# P3 — RUN — DRAFT v0.7.5
Entry: `/wow-run <run-id>` · Output: `runs/<run-id>/RUN-REPORT.md` + commits · No human in the loop by design.

## [ORCH] — branch & merge model (the parallel-execution contract)

- Create `wow/<run-id>/base` **from the configured run base** — `run_base` in wow.config.json, defaulting to `main_branch`, defaulting to `main` (v0.7.3, prodsim/F-65: a repo adopting WoW on a feature branch followed 'from main' into a base 258 commits stale on which the run did not exist — no plan, no gates, and a mutation proof that would have 'restored' 258 commits of unrelated history; a convention key, ORCH-consumed like `jira.scope`). **Assert it mechanically at run open**: `gates.sh check-id <run-id> --base <ref>` refuses a base that does not carry the run's plan. At run start; `wow/<run-id>/int` from base; one worktree + branch `wow/<run-id>/U<n>` per unit — **cut from `int` as it stands at the close of the previous wave** (v0.7.2, F-58; wave 1 ≡ base). This is what the wave ordering is FOR: a wave-N unit can read a wave-<N artifact because its branch carries it. Under the old cut-everything-from-base model a unit's declared cross-unit inputs were unreachable by construction, and the silent failure was an executor re-creating consolidated work inside its own ownership — green on every gate. A SAME-wave producer stays unreachable even now; GATE-8 refuses that plan shape at G2 (`inputs:`, P2).
- Executors commit **only** to their unit branch. **Only the ORCH merges.** After a unit's verifier PASS: **`git merge --no-ff U<n>` into `int`** (the merge commit carries the bare `[T:<run-id>]` trailer; merges are exempt from GATE-1's phase-artifact scope rule, LANES) — sequentially, in wave order; **never rebase** (v0.7.2, platform/F-60: FORMATS §3 tells executors to cite `ev:commit{<sha>}` and a rebase rewrites every one of those shas into dangling objects — the linear history it bought was worth less than evidence that resolves; the mechanical resolver for the class is OBL-PKG-23). No force-push anywhere; `main` is never touched mid-run.
- **Conflict policy:** conflicts inside a unit's owned paths are impossible by construction (GATE-8 partitioned them) — if one occurs it is a **plan defect** `DEF-plan-<nn>`: log it, ORCH resolves (owner unit's version wins unless integration contract says otherwise), record `ev:commit`. Conflicts in generated/lock files: resolve by regeneration, never hand-merge.
- Integration wave executes on `int` (same executor/verifier discipline). Run reaches `main` only after integration verify passes — PR or fast-forward per `wow.config.json`.
- **Mid-run plan amendment (added v0.6.3, F-16):** a PO decision may amend the signed PLAN mid-run (new task, widened ownership, changed contract) — record it as an `AM-<nn>` line in the plan (FORMATS, F-29). After ANY plan amendment the **ORCH merges the run base into every live unit branch**; a unit blocked on an unmerged amendment is an ORCH action, not a park. Base→unit happens at wave open AND after each amendment — the second case is the one that was undescribed and cost a full agent cycle. **An amendment binds when it is COMMITTED to the branch units branch from** (v0.7.2, F-54): the plan is a file in git, so the edit has a commit boundary the docs never named — an amendment authored, linted green, cited in a brief and uncommitted matched nothing on any tree a unit could see. At each wave dispatch the ORCH resolves every amendment id the brief cites against the unit's branch point (`git grep <id> <branch>` is the whole check) and does not dispatch on a miss; the good outcome of skipping this is a park, and the bad one is an executor reconstructing a plausible amendment from the brief's one-line gloss. **A re-dispatch** (v0.7.5, prodsim/F-104) — a unit that already ran, dispatched again at a later boundary for an amendment's task — branches from `int` at that boundary, is recorded on the amendment, and the plan carries it as `dispatched_at_wave: <n>` on the unit (`wave:` keeps meaning where the unit's outputs first appear). **ORCH records a unit must read** live under `runs/<id>/orch/` and are declared as that unit's `inputs:` (prodsim/F-108); before cutting a wave the ORCH runs `gates.sh gate-8 --run <id> --boundary <wave>`, which refuses the cut while any such record is missing from `int`.

## [ORCH] — orchestrate

1. Start 3–4 concurrent executors, fresh context each. Executor manifest = its unit's PLAN section + **the plan's `## Contracts` block (every unit, always — F-28: the unit section is the only channel to an executor, so a rule that binds all units lives there or reaches nobody)** + interface contracts + CONVENTIONS + the `[AGENT]` sections of this file. **Nothing else.**
2. After each unit's executor finishes → spawn its **verifier AGENT** (fresh context; different model where possible; manifest = that unit's SPEC ACs + contracts + verify commands + `[AGENT] verifier` section; **never the implementer transcript**).
3. Verifier findings (`VF-U<n>-<nn>`) → fix wave in executor context → **re-validate every fix** (verifier context, delta scope). Loop until clean or parked (FORMATS §7). A unit's repair of its OWN report or evidence in a fix wave is labelled by the finding it answers — `repairs VF-U<n>-<nn>` in the report — never by an invented id shape (v0.7.5, platform/F-90: `AM-` belongs to plans and the ORCH; one unit minted `AM-VF-U4-nn`, inert and indistinguishable from plan amendments in a bare grep).
4. **A defect in a contracted CHECK (added v0.6.3, F-22):** when the fix is a plan amendment, its only possible author is the ORCH (FORMATS §9) — the one actor with a standing interest in the grade. So a plan-amendment-as-fix gets its own delta verifier whose manifest **names the amendment as the object under test**; it allocates findings in the AMENDMENT's segment, `VF-AM<nn>-<nn>` (and `CV-<run-id>-AM<nn>-<nn>`), and writes `runs/<id>/reports/AM-<nn>-verify.md` — a path that is nobody's unit output (v0.7.5, platform/F-93/F-95 + prodsim/F-105: two verifiers allocating in one unit's segment minted one VF id for two findings, and six reports partitioned a segment by forward notes); it also classifies each finding's fix-budget class — `repaired` / `spent` / `carry-forward` — in its grade row; the ORCH copies every such class, and every `DEV-ORCH-<nn>` with the verifier's in-contract verdict, into the `## ORCH classification` table of `walk-G4.md` (`| id | verifier class | overrule |`, FORMATS §4), where the PO overrules by filling the third cell at G4 and is never asked per item (v0.7.5, platform/F-96 + prodsim/F-103; `orch_classification`, FORMATS §7; DEV-R12-11 named the missing surface). The brief instructs premise-failure attempts against it ("assume nothing is fixed until you have made the check fail on purpose"), and the amendment states what coverage it gives up. This path was improvised once and found a real hole on its first outing (VF-U5-02). **Provenance clause** (v0.7.4, prodsim/F-85 — the machinery worked three times in one run and found a hole every time, and both late findings were provenance failures the docs never named): an amendment's supporting evidence must be **re-derivable from tracked state that existed independently of the amendment** — evidence generated by the amendment's own artifacts does not count, a directory is not provenance, and a check that consumes an enumerated exemption/exclusion list requires each entry's proof to resolve against a git-TRACKED file that is not an output of the check itself. The verifier's brief names this in the same register as the premise-failure instruction: *find where the amendment's evidence comes from, and try to manufacture it.* The achievable bar is refusing untracked and self-generated evidence and keeping list growth reviewable in git; it is not proof against deliberate manufacture, and the brief says so.
5. **Wave boundaries — history, then sweep `int`.** Before merging `wow/<run-id>/U<n>`, run `gates.sh history --run <run-id>` in the checkout that holds the branches: it refuses any unit branch whose reflog carries a reset, rebase, amend or `branch -f` since the branch was cut (v0.7.5, prodsim/F-99: a verifier soft-reset its own report commits and the discarded commits survived only in a local reflog P5 never archives). A refused branch is NOT merged: the ORCH restores the discarded tip(s) from `git reflog show <branch>` as NEW commits on top (`git cherry-pick -n <sha>`, commit), records a `DEV-ORCH-<nn>` naming the rewrite, re-runs the check, then merges (DEV-R12-10). Then (v0.7.3, prodsim/F-70) run `gates.sh sweep --run <run-id>` ON the integration branch at every wave close — 43 findings once rode two merges because the run's own gate was never pointed at the run's own merged tree, and the ORCH's instinctive substitute (sweeping the branch underfoot) passed vacuously: **the branch under your feet is not the branch under test** — scan targets follow the checkout. Gates with a registered subject label print their count, and the sweep summary aggregates the vacuous ones, so a vacuous green says so.
6. **Wave boundaries — reconciliation walk (added v0.6.3, F-25):** executors exit their context and never return to their rows, so a `BLOCKED`/`PARKED`/`FAILED` row whose blocker was discharged elsewhere stays wrong until someone walks back — ten stale rows across five reports in one measured run, and the derived view false for days. At every wave boundary the ORCH walks open parks and BLOCKED/FAILED rows and closes any whose named blocker is discharged, **preserving the original grade in a dated reconciliation note** (the contemporaneous observation is not rewritten away). The Jira side is the SAME step, not a separate one: transition each unit's story as its executor finishes and its verifier passes — seven stories at Intake through four waves was one structural omission, recorded on both sides of the git/Jira split.
7. **Wave boundaries — cascade rule (ORCH only, never executors):** mark every task downstream of a PARKED/BLOCKED task as `BLOCKED(cascade:<source-id>)`; independent tasks proceed. **If >50% of the next wave is cascade-blocked, terminate the run early → P4.**
8. Tier escalation per P2 §tiers at wave boundaries. Assemble RUN-REPORT.md from `reports/*.md`; maintain HANDOFF.md. (PLAN, RUN-REPORT, HANDOFF, jira-queue, walk-G4, `orch/*` are ORCH-owned — FORMATS §9.) **Before the RUN-REPORT commit, re-run every `ev:cmd` a COMPLETED AC row cites against the `int` tip** and cite the re-run (v0.7.5, prodsim/F-93: a verifier's own report commit, 14 minutes after its re-run, planted text that flipped the check it had just re-derived, and the RUN-REPORT cited the stale figure 36 minutes later — the window between the last verify and the citation is structural, and this step closes it). **Commit messages state the claim and cite the artifact for the figure** (v0.7.5, platform/F-89): counts, ids and measured values live in files that can be amended — a commit message cannot be, and `ev:commit{<sha>}` sends a reader straight to it; a correction to a commit-message claim is one RUN-REPORT line keyed to the sha, and a `VF-`/`CV-` id minted only in a commit message resolves to nothing. <!-- steps renumbered sequentially, DEV-R9-13 -->

## [AGENT] — executor

- Do only your task list, in order, on **your unit branch only** — never merge, rebase, push shared branches, or touch files outside your ownership list.
- One atomic commit per task, message with `[T:<task-id>]`. Each task: implement → run its verify command — the RUNNABLE form is `scripts/wow/gates.sh verify-cmd <task-id>`, the cell with its `\|` escapes removed (v0.7.5, prodsim/F-111) → record `ev:cmd` in your report file — **and paste the command's actual output under it, fenced** (v0.7.1, F-43): GATE-3 proves a citation's form, never its truth, and a fabricated citation is well-formed by construction. The paste costs nothing when the run was real and gives your verifier a concrete artifact to diff against its re-run — it raises the cost of fabrication without being proof against it (the re-run is the truth check). Describe-instead-of-paste is the tell. **A paste comes from a capture, and names it** (v0.7.5, prodsim/F-95/F-96): write the output to a file under `runs/<id>/evidence/U<n>/` with one committed, re-runnable capture script, put `capture: <path>` on the line above the fence, and GATE-3 compares the fence with the file byte for byte at every sweep — AFTER the repo's formatter has run, which is when prettier rewrites `*…*` to `_…_`, escapes a bare `*` and strips trailing whitespace inside fences (four pastes in one run stopped matching their captures and two citations stopped running as written). Your last Verify re-runs the capture script into a fresh directory and diffs it against the evidence directory. **For every check you write, name where its expected value comes from** (v0.7.5, platform/F-105): if it comes from the artifact under test or from a file generated by it, the check is oracle-shaped — its expected value derives from its own subject, so it passes by construction — and needs an independent oracle or a plant that would fail on a wrong subject — a passing plant that should have failed is parked, not explained away.
- **Autonomy contract:** in-contract deviation → decide, implement, log `DEV-U<n>-<nn>` (what/why/impact). Cross-unit, AC-touching, or irreversible → **park**: `PARK-U<n>-<nn>` blocker note (facts only), skip, continue. Never ask questions; anomalies are parked, not investigated (the ORCH routes them to the debug lane after the run).
- Write only `runs/<run-id>/reports/U<n>.md`: per-task status (FORMATS §4 + `ev:`), deviations, parks, observations.
- **Captured responses are scrubbed before commit** (v0.6.4, PII): third-party personal data is trimmed at capture time and the trim is RECORDED in the capture file (what was removed and why) — a declared trim is honest evidence; a silent one is the defect the capture-whole rule forbids; an undeclared populated field is refused by GATE-14 at commit. A deliberate capture carries `pii-ok: <reason>` in the file, visibly.

## [AGENT] — verifier

- Two verification modes (added v0.6.3, F-30). **Re-derive** (default): run every AC and task verify yourself; record your own `ev:`; do not trust recorded results — the re-run IS the framework's only truth check on executor citations (v0.7.1, F-43): a report whose `ev:cmd` rows lack pasted output is the cue to re-run everything it cites, and a cited result that cannot be reproduced even approximately is a `VF-` finding about the citation itself, not a formatting nit. **Audit** — for tasks the PLAN marks `audit-only: <why>` (evidence destroyed by the procedure itself, credential contractually held by a human, re-run destructive/costly): do not re-run; instead check that every contracted clause has a citation, that each recorded conclusion follows from the recorded output, and that **each recorded check could have failed** — a check whose evidence reads identically under a wrong outcome is the finding. The PLAN marks audit-only tasks at P2, in front of the PO at G2 — never the ORCH at spawn time, which lets the party under review scope the verifier away from its weakest evidence.
- Attempt the premise failure on flagged ACs (flagged = the spec's harness-touching cell reads `yes`, P1 step 3): check the thing the AC is *about*, not the harness. Grade the executor's stated oracle source for every check (platform/F-105).
- **Your history is append-only** (v0.7.5, prodsim/F-99): commit only to your unit branch; never `reset`, `commit --amend`, `rebase` or otherwise rewrite a commit once made — a correction is a new commit (`gates.sh history --run <id>` refuses a rewritten branch at the wave boundary). Do not spawn sub-agents; if the host cannot prevent it, record every delegation in your report.
- Grade: PASS / PASS-with-carry-forwards / FAIL (`VF-U<n>-<nn>` with evidence). **A carry-forward grade means: ALLOCATE a cannot-validate record per FORMATS §5 — in your unit segment, in your report — and cite its full `CV-` id in the grade row** (v0.7.3, prodsim/F-69: three verifiers in one run read the old parenthetical as provenance, recorded carries as `VF-`/`CF-` ids, and GATE-3 refused five rows at once — at integration, after everyone's context was gone). **Before handing back, run `gates.sh gate-3 --paths <your report>` yourself**: the gate that grades your report's form runs in the ORCH's loop, not yours, and a report that fails it costs a cycle at the worst moment — **tabulate grades under a `Grade` or `Verdict` header** (GATE-3 checks that column against the verdict vocabulary, FORMATS §4; a grade in a Status/Result column reads as a status and is rejected). Write only `reports/U<n>-verify.md`. If you need context, read code and contracts, not transcripts.

## RUN-REPORT.md structure [ORCH]
`completed / failed / blocked / parked / deviations / defects / new-gaps` — rows per FORMATS §4–5, every completion row evidence-cited (GATE-3), one line per row. Plus an `## audit triggers` table — `| AT-n | value | ev |` rows (table rows, never bullets — the deriver reads rows; a heading suffix like `## audit triggers — recorded at P4` is fine since v0.7.5, platform/F-87) for the orch-derived counters: **AT-1 = stand-ins for real systems committed this run** (v0.7.5, prodsim/F-100 — ONE definition, the role, not the path: the old example counted every path under `fixtures/` and read 126 where the stand-in inventory read 0; not a stand-in: non-vacuity controls (v0.7.2, F-47), parser/formatter inputs whose tests assert parsed values, synthetic data labelled as such, trimmed captures of real responses used as test input; a stand-in: code or data that replaces a real system on the path of a product AC) — what survives in the tree at run end, not filesystem events mid-run (v0.7.1, F-40), derived from a stand-in inventory diff BASE vs TIP at the run boundary; **AT-2 = remediation cycles as P4 step 5 defines them** (one per trigger, cited as a runnable command over COMMITTED artifacts — GATE-7 refuses the row without an `ev:cmd` — v0.7.5, platform/F-101 + prodsim/F-91). status.mjs READS these from here (v0.6.4, F-33 — recording them anywhere else moves the derived view not at all).
